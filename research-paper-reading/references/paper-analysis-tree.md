# 论文解析树

解析树用于边读边回答问题。节点间应形成因果关系：旧方法的限制产生技术挑战，观察或洞见导出设计，设计由证据验证。不要把目录标题机械搬成树。

## 1. Task / Problem

- 研究对象、应用场景和利益相关者是谁？
- 输入、输出、目标和成功标准是什么？
- 这个问题为什么重要？重要性来自准确性、效率、规模、安全、成本、可用性，还是新能力？
- 问题是否真实存在，还是由特定数据集、基准或假设构造出来？

## 2. Prior approaches and technical challenges

对每条主要前作路线建立同构节点：

- 基本做法与适用条件；
- 已解决的问题；
- 当前任务下的 limitation 或 failure case；
- limitation 背后的技术原因；
- 本文是否提供了证据证明该问题确实存在。

把“前作不好”改写成可验证的技术挑战。例如不要只写“速度慢”，而要写明瓶颈来自算法复杂度、通信、内存、串行依赖、实现或硬件。

## 3. Observation / Insight

- 作者观察到了什么现象、规律、结构或机会？
- 观察来自理论、数据、实验、系统 profiling、用户行为，还是经验直觉？
- 这个观察是否足以推出所提方法？中间缺少什么假设？
- 是否存在更简单的替代解释或设计？

这是“为什么这样设计”的桥梁。若论文没有明确给出，标记为论文叙事缺口，不替作者补写。

## 4. Contributions

区分贡献类型：

- 问题或任务定义；
- 新观察或实证发现；
- 算法、模型或理论；
- 系统、工具或基础设施；
- 数据集、基准或评价协议；
- 用户、社会或安全结论。

对每项贡献回答：新在哪里，相对哪个最近前作，解决哪个挑战，代价和新限制是什么。

## 5. Method / System

先给 overview，再为每个 pipeline module 建立四个固定子节点：

1. **Motivation**：该模块针对哪个挑战或上游问题？
2. **Mechanism**：输入、操作、状态、输出和训练/运行过程是什么？
3. **Difference**：与最相近前作、标准组件或朴素方案有何实质差异？
4. **Technical advantage**：为什么预期更好，收益在哪个条件下成立，付出什么代价？

最后检查模块间关系：顺序、共享状态、反馈、资源竞争、错误传播和端到端目标。局部最优不等于系统最优。

## 6. Evidence / Experiments

按“主张”而不是按论文表格顺序组织证据：

- **比较实验**：核心方案是否优于合适且公平的基线？
- **消融或对照**：每项核心贡献是否真的影响结果？组件间是否有交互？
- **机制验证**：结果变好是否因为作者声称的原因，而非数据、预算或实现差异？
- **鲁棒性和边界**：不同数据、规模、负载、硬件、随机种子、用户群体或攻击者下是否成立？
- **成本**：时间、空间、能耗、数据、标注、硬件、运维和人力代价是什么？
- **失败案例**：失败是否呈现稳定模式，是否与核心假设相关？

每项证据记录协议、变量、对照、结果、支持强度和替代解释。

## 7. Limitations and failure cases

- 作者明确承认了什么？
- 哪些关键假设未被测试？
- 在什么输入、分布、规模、负载、硬件、威胁模型或用户群体上可能失败？
- 新方法在带来收益的同时引入了什么更强限制？
- 失败需要通过阅读代码、复现实验或额外压力测试才能发现吗？

把泛泛的“泛化有限”具体化为可构造的 failure case 和最小验证实验。

## 8. Literature-tree position

- 本文继承哪篇 milestone paper 或哪条技术分支？
- 它解决或重新定义了哪个 milestone task？
- 是关键转折、增量优化、工程规模化，还是负结果/边界修正？
- 它改变了对哪些前作的判断？
- 应新增哪些节点和连边？下一篇最关键的前向或后向文献是什么？

完成这一层，才算从“读懂单篇论文”上升到“理解领域如何演化”。
