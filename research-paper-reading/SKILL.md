# 计算机论文深度阅读

目标不是逐段复述，而是以合适的阅读成本建立可复用理解：论文解决了什么问题，旧方法为什么不够，作者凭什么提出新方法，证据是否支持结论，它改变了哪条技术路线，以及下一步应读、应复现或应验证什么。

## 开始前

1. 确认可访问的材料范围：论文正文、补充材料、官方代码或 artifact。只有题目时，请求 PDF、链接或正文；只做初筛时可用摘要与结论。
2. 记录题目、作者、年份、出处、版本和材料范围。区分预印本、正式版本与后续修订。
3. 判断论文的主要证据类型，并只读取 [references/domain-checklists.md](references/domain-checklists.md) 中相关部分。跨类型论文组合使用。
4. 除非用户指定深度，按三遍流程逐级决策；不要默认把每篇论文都读到同样深度。

始终标记信息性质：

- **论文事实**：正文、公式、代码或图表直接支持的内容，附页码、章节、图、表、公式或文件位置。
- **分析推断**：由证据推导出的解释，标注“推断”。
- **研究假设**：尚未验证的延伸，标注“假设”或“待验证”。

材料未报告时写“论文未报告”或“当前材料不足”，不得补造实现细节、数值、因果解释或作者动机。

## 第一遍：快速海选

阅读标题、摘要和结论；必要时查看问题定义、方法总览图、实验主表和 limitations。回答：

1. 研究对象和核心问题是什么？为什么值得解决？
2. 作者声称的关键洞见、贡献和结果是什么？
3. 这是新问题、新观察、新方法、新系统、新理论、新数据，还是新的实证结论？
4. 它与用户目标或当前 literature tree 有什么关系？

分别以 0–5 分评估：相关性、潜在贡献、证据可信度、继续阅读价值。每个分数附一句可核验依据，不计算伪精确总分。

给出决策：

- **停止**：弱相关、贡献有限，或证据明显不足。
- **进入第二遍**：需要理解方法逻辑、实验或与前作的关系。
- **直接进入第三遍**：用户明确要求精读，准备复现/采用，或关键技术细节会改变研究决策。

若停止，仍按 [references/report-template.md](references/report-template.md) 输出快速筛选版。

## 第二遍：用论文解析树通读

完整通读论文，但暂时跳过非关键证明、推导和实现枝节。阅读时同步构建 [references/paper-analysis-tree.md](references/paper-analysis-tree.md)，把论文变成一组有依赖关系的解答题，而不是章节摘要。

必须回答六个核心问题：

1. **Q1 问题**：任务、应用场景、输入输出、目标、假设与约束是什么？
2. **Q2 脉络**：此前有哪些技术路线？它们分别在哪个技术挑战上失败或受限？本文处在 literature tree 的哪个位置？
3. **Q3 洞见与方法**：作者观察到了什么，为什么由此推出当前方案？每个核心模块的动机、操作、相对前作的差异和技术优势是什么？
4. **Q4 证据**：比较、消融、理论、系统测量、用户研究、案例或形式化验证分别支撑哪项主张？
5. **Q5 局限与探索**：方法在哪些输入、规模、分布、负载、威胁模型或用户群体上可能失败？哪些结论仍缺少证据？
6. **Q6 总结**：用“问题—挑战—洞见—方法—证据—边界”六句话总结论文。

### 图表和实验优先

对每张关键图表说明：它要回答什么问题，变量、轴、列和对照是什么，协议是否公平，结果支持哪项主张，是否存在异常、反例或替代解释。不要只抄数字；同时解释绝对差距、相对趋势、统计或工程意义。

建立“主张—证据—缺口”矩阵。若强主张只由单一数据集、单一工作负载、定性样例、不充分消融或作者自定义指标支持，应降低可信度。

### 相关文献和领域位置

仅圈出理解或判断本文不可缺少的文献，按以下角色组织：问题源头、方法前身、里程碑、最强基线、竞争路线、数据/指标/理论来源、后续工作。说明每篇“为什么需要读”。

完成后判断是否进入第三遍。优先精读：与课题直接相关、准备复现或采用、可能更新 milestone task，或存在关键疑点需要核验的论文。

## 第三遍：机制、系统与复现

以“能够重建、质疑和最小验证”为完成标准。必要时阅读官方代码辅助理解术语、实现和隐含选择，但不得用代码中不存在的行为解释论文。

1. 逐项解析影响结论的术语、定义、公式、算法、接口和实现选择；对公式说明符号、定义域、目标、直觉、假设与边界。
2. 重建端到端系统：边界、输入、状态、组件、依赖、交互、反馈、输出和资源约束；追踪错误或偏差如何跨组件传播。
3. 将总贡献拆成最小可验证单元，区分算法、数据、系统工程、硬件、预训练、调参和评测协议带来的收益。
4. 从 [references/domain-checklists.md](references/domain-checklists.md) 选择合适的可信度检查：统计有效性、证明条件、性能测量、威胁模型、用户研究或形式化保证。
5. 做反事实和压力测试：移除模块、改变数据/负载/规模/硬件/攻击者/用户群体、违反关键假设后，结论是否仍成立？
6. 形成最小复现方案：依赖、数据或工作负载、配置、评测脚本、资源、成功判据和待确认项。先设计低成本的关键性实验，再规划完整复现。
7. 更新 literature tree：本文解决了哪个 milestone task，是否创造新分支，哪些旧结论应修改，下一篇最值得读什么。
8. 提出 2–5 个可执行研究方向，每个写明依据、具体改动、最小验证、预期收益和主要风险。

复杂方法可用 Mermaid 流程图、依赖图或模块表重建；只在它能澄清数据流、调用关系、反馈环或故障传播时使用。

## 输出要求

使用 [references/report-template.md](references/report-template.md) 组织结果，并根据实际阅读遍数删除未完成部分。先给结论和下一步决策，再给证据与细节。

- 保留论文原始术语，首次出现时给出中文解释或定义。
- 关键判断附页码、章节、图、表、公式、代码文件或实验位置。
- 跨论文数值比较前核对数据、工作负载、硬件、预算、实现、指标和统计协议；不可比时明确说明。
- “作者声称”“证据显示”“我的推断”“研究假设”必须可区分。
- 用户有明确问题时先直接回答，再补完整解析树。
- 不因模板完整而填充低价值内容；优先保留会改变理解或决策的信息。
